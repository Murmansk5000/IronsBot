# IronsBot 架构工作约定

本文规定架构改动如何被设计、实施、审查与收口。它补充
[ARCHITECTURE.md](../ARCHITECTURE.md)：后者定义代码目标与边界，本文定义
后续工作如何持续向该目标推进。

## 设计来源与冲突处理

`ARCHITECTURE.md` 是长期架构目标的唯一规范来源；当前代码、旧设计记录和
过渡实现都不是新设计的授权。每次开始跨模块工作前，先标明它处理的是
`target`、`transition` 还是 `baseline` 契约。

### 文档层级与唯一目标

架构工作中的文字按以下顺序解释，不能把不同层级的内容并列为两套“最终
设计”：

1. 用户已确认的需求或阶段计划定义本次要改变的产品范围；
2. `ARCHITECTURE.md` 定义持久的目标契约、所有权和删除条件；
3. 本文定义设计、验证、迁移和提交的工作方式；
4. 已验证代码定义当前 `baseline` 或 `transition` 的事实；
5. 旧 prompt、历史计划、提交说明和注释只可作为调查材料，不拥有当前设计
   授权。

当第 1 项要求改变第 2 项的目标时，先在同一工作项更新
`ARCHITECTURE.md`，明确旧目标是否退役、当前桥接保留什么以及新的完成条件；
之后才能开始代码迁移。不得让任务 prompt、README、设计草稿或代码注释各自
维护另一份长期目标。未能确定这种变更时，工作项应保持 `blocked`，而不是把
两个相互矛盾的方案一起实现。

当新版阶段计划与文档中的旧表述不一致时：

1. 以经确认的新版阶段计划为目标；
2. 在同一工作项中修正文档，使“当前实现”“迁移桥接”和“最终目标”明确分开；
3. 不用兼容层、第二份清单或双读逻辑回避冲突；
4. 在代码尚未迁移前，如实保留 `transition` 状态和删除条件。

### 文档事实与术语校验

架构文档中的每一条“当前”断言都必须能指向已验证的代码、测试或已发布的数据
schema；没有该证据时，只能写成 `target` 或 `transition`，不能以未来类型名、设计
草图或计划编号把它伪装成现状。反过来，已退役类型也不能因为历史分支仍出现它，
就被重新写成当前的唯一契约。

每次修改架构文档、合并架构分支或标记阶段完成时，必须做一次术语校验：

1. 搜索本次退役或改名的类型、模块和旧权限归属，确认它们只保留在历史或迁移说明；
2. 搜索 `唯一`、`当前`、`已完成`、`目标` 等状态词，确认每个职责只有一条权威表述；
3. 核对 `ARCHITECTURE.md` 的 Transition Inventory、包结构、阶段完成条件与真实代码；
4. 对尚未落地的目标，写清当前桥接、禁止新增的职责和删除条件；
5. 将发现的不一致作为未完成工作项记录，不能为了让文档好看而把阶段标为完成。

这项校验是设计工作的一部分，而不是文案润色。它避免不同分支都由同一人编写时，
仍因写作时间不同而留下相互冲突的架构叙述。

例如，标准 NoneBot TOML 插件清单与配置化的清单 profile 选择器属于目标
插件装载方式；禁止的是额外的反射发现、应用私有模块列表或运行时服务定位器。
当前标准 TOML 先声明需要在本地插件前加载的第三方依赖，再直接发现每个内置
本地插件。临时 OneBot bootstrap 仅适配已配置的私有扩展，不能因它仍在运行而
被误当成未来插件、命令或生命周期的权威。

### 合并架构文档

Git 只能发现同一行附近的文本冲突，不能判断两份架构表述是否在描述相同职责。
合并涉及 `ARCHITECTURE.md`、本工作约定或设计记录时，必须先按语义处理，再写
入最终文本：

1. 识别每一侧分别陈述的是 `baseline`、`transition` 还是 `target`；
2. 保留已验证的当前事实，但明确标记为当前或过渡状态；
3. 保留经确认的目标和它的完成条件，不因当前代码仍在使用旧接口而倒退目标；
4. 对同一职责只保留一条权威表述，不能用两段互相矛盾的文字或“都保留”解决；
5. 将已退役接口只留在历史/迁移说明中，不能在合并后恢复为当前契约；
6. 合并完成后检查目录、职责表、过渡清单和阶段完成条件是否仍相互一致。

若冲突无法在本工作项内判断目标优先级，应停止合并并记录待确认问题；不能依靠
Git 的 `ours`/`theirs` 策略静默选择整段文档。每次这种语义合并都要在提交说明中
写出处理的职责及最终保留的目标，方便后续分支复用同一判断。

## 先设计，再落代码

每个任务开始前必须写出最小设计记录。它可以是一段简短说明，也可以是
完整计划，但必须包含：

| 项目 | 必须说明的内容 |
| --- | --- |
| 目标 | 用户或系统真正要解决的问题，而不是准备修改的文件名。 |
| 契约状态 | `target`、`transition` 或 `baseline`；含义以 `ARCHITECTURE.md` 为准。 |
| 所有权 | 领域服务、端口、仓储、渲染器或插件中谁负责此行为。 |
| 复用 | 已有接口如何复用；若新建接口，为什么它是通用的最小边界。 |
| 范围 | 涉及的仓库、公开行为、配置、数据结构及不在本次范围内的事项。 |
| 数据 | 数据来源、主键、生命周期、迁移和回滚方式。 |
| 验证 | 有针对性的测试、静态检查、编译检查和必要的真实流程检查。 |

不能因为某个插件、SQLite 文件、正则或后台任务已经存在，就把新需求继续
堆到那里。相同语义的输入、身份、命令、状态、通知或渲染需求，应先寻找
现有通用接口；没有合适接口时，创建有明确领域归属的小接口。不得用
`utils`、`shared`、`common`、全局服务定位器或万能仓储掩盖所有权。

## 持续任务工作项

跨仓库或持续多轮的任务必须拆成可独立验证的工作项。每个工作项开始时都
记录以下内容，并在调查改变范围时立即更新：

| 项目 | 要求 |
| --- | --- |
| 工作项边界 | 一次只迁移一个职责、一个数据契约或一个明确的用户行为。 |
| 前置条件 | 需要先发布的数据 schema、先完成的仓库提交、配置或真实数据样本。 |
| 完成条件 | 唯一正常路径、删除项、针对性测试和 smoke test。 |
| 回滚点 | 可回退的提交、数据备份或不替换生产文件的验证方式。 |
| 预计时间 | 总任务、当前阶段和当前工作项的估算；它是可调整的预测，不是对用户的承诺。 |

工作项不能以“已经写了一些代码”完成。只有完成条件被实际验证后，才可以
标记完成并推进下一项。发现被其他分支修改的文件时，先确认它属于用户改动、
已验证的当前实现，还是待合并的目标态；不得为了继续实现而覆盖它。

架构文档本身也遵循这个规则：文档只可以描述已验证的当前状态、明确标为
`transition` 的桥接，或有完成条件的目标。它不能把尚未落地的设计写成“当前
唯一实现”，也不能因为 Git 合并冲突恢复已经退役的接口。

### 可复制工作项模板

新的持续工作项必须先以以下格式记录在计划、任务说明或对应设计文档中。短小的
修复可以合并为一段，但不得省略契约状态、所有权、验证和回滚点：

```text
工作项：<清晰的领域职责，而不是文件名>
状态：planned | in_progress | blocked | completed
契约：target | transition | baseline

目标：<要保留或改善的用户/系统行为>
所有权：<服务、端口、仓储、渲染器或平台适配器>
复用：<复用的既有类型、端口、解析器或迁移工具>
范围：<会改动的仓库、公开行为、配置和数据>
不在范围：<本次明确不处理的相邻职责>
迁移：<旧路径、一次性迁移工具、备份和删除条件；无则写“无”>
验证：<针对性测试、静态检查、编译和 smoke test>
回滚：<可回退提交或数据恢复点>

进度：<总任务 / 当前阶段 / 当前工作项>
预计：<当前估计和置信度；范围变化时更新原因>
```

一个工作项只能在“验证”实际通过且迁移/删除条件满足时标记 `completed`。若发现
范围扩大，先拆出新的工作项并更新预计，不能把未验证的后续债务藏在同一个“重构”
提交里。跨仓库的前置提交、发布顺序和消费端 smoke test 必须写在同一条记录中，
以便任一仓库单独更新时仍能判断兼容边界。

持续任务的进度报告同样是工作记录的一部分：每次开始、完成工作项、发现范围变化
或遇到阻塞时，都更新总任务、当前阶段和当前小任务的已验证进度与预计时间。预计
必须说明它基于哪些尚未完成的验证；不能把“已写代码”计入完成比例，也不能在没有
证据时承诺固定完成时刻。

## 代码层次检查

在实现前和代码审查时，逐项确认：

1. 插件仅做事件适配、调用服务和发送结果；不在插件中拥有可复用业务规则。
2. service 不导入 NoneBot、OneBot、QQ Official 或具体插件类型。
3. renderer 只接收视图模型与资源，不读 SQL、不发 HTTP、不猜业务关联。
4. integration 实现明确端口；它不决定用户文案、权限或产品策略。
5. 配置、帐号、群号、链接、令牌和部署选择不写死在业务代码。
6. 同类命令只在 `CommandCatalog`/`CommandContract` 处登记一次；帮助、戳一戳
   和 AI 认领都从同一描述查询。
7. 所有需要赛尔玩家 ID 的位置复用 `PlayerIdResolver`；实体别名复用统一别名
   解析契约，实体自己的规范化与存储仍归实体所有。
   输入层的 `*TargetCommand` 可以保留原始引用；传入 service 的业务命令必须只
   携带已验证的数字 ID。解析器在平台边界执行一次，service 不得再次解析别名、
   `@` 成员或默认绑定。
8. 平台身份使用不透明字符串 `ActorRef`/`ConversationRef`；OneBot QQ 号与
   QQ Official OpenID 不隐式互转。
9. 正常运行路径只读写一种 schema；旧数据仅由停机的一次性迁移工具处理。
10. 配置字段迁移同样只能由部署迁移说明或一次性工具完成；模型不得静默把
   `refresh_hour`/`refresh_minute` 等旧字段改写为新字段。无法识别的字段必须在
   启动时明确报错，当前配置只接受 `time = "HH:MM"`。
11. 新生产 Python 模块必须遵守 800 行限制，并按真实职责拆分，不能把代码
   移进无归属的辅助文件来规避检查。
12. 平台身份在持久化层只使用 `ActorRef` / `ConversationRef` 的独立列；QQ
   数字只能存在于 OneBot 适配边界。旧 SQLite 的列形状只能由停机迁移工具
   读取，运行时代码不得双读、补列或懒迁移。
13. 迁移到标准 NoneBot 清单的插件必须同时拥有自己的 `PluginMetadata`、
   `PluginContribution` 和直接命令描述；不得把 matcher 留在中央桥接、
   把帮助或命令元数据留在另一处。
14. 迁移出站消息时保留原有发送语义：`OutboundMessenger.send()` 是主动推送，
   必须经过目标平台的队列、限流和退订策略；`reply()` 才是对当前事件的即时
   回复。不能因为换成通用端口而绕过防刷屏、路由或失败回滚。
15. 通知服务的收件人必须使用 `ActorRef` 或 `ConversationRef`；OneBot 数字
   目标、`MessageTarget`、`OneBotDelivery` 和 CQ 消息只能留在 OneBot 适配层。
    迁移中的适配器可以复用旧投递链以保留队列、退订和限流，但不得把这些类型
    重新传回 service。

## 插件术语与权威边界

不能再把插件相关对象统称为“唯一插件契约”。它们职责不同，后续设计和代码
审查必须使用准确名称：

| 需要描述的事情 | 唯一权威 |
| --- | --- |
| 插件静态身份与 NoneBot 元数据 | `PluginMetadata` |
| 插件安装时提交 matcher、job、hook 等运行时贡献 | `PluginContribution` |
| 用户可输入命令的语法、示例、权限、帮助、戳一戳与 AI 认领 | `CommandCatalog` / `CommandContract` |
| 某个用户或会话是否有功能权限 | feature-policy service |
| 进程生命周期、后台任务与关闭顺序 | `ApplicationLifecycle` |

`PluginDefinition` 已退出当前架构。除迁移记录或 Git 历史说明外，不得在新代码、
测试、计划、图示或文档中重新引入它，也不得以“临时方便”为由恢复中央插件注册
表。`PluginContribution` 只是一项插件局部的运行时提交记录，不能承担命令目录、
权限策略、帮助布局或跨插件生命周期等第二份权威。

当前代码中的 `CommandDescriptor` 是目标 `CommandContract` 的过渡载体，并非另一
套命令权威。`CommandCatalog` 已是唯一目录；新增命令能力必须扩展同一描述和同一
查询接口，让帮助、戳一戳和 AI 认领共同消费。不得因为最终类型尚未改名，就新增
第二份命令表、matcher 私有关键词或 AI 私有白名单。

计划和提交必须准确区分术语：`CommandDescriptor` 写为“当前命令契约载体”，
`CommandContract` 写为“目标类型”。只有所有直接命令都通过统一契约注册、
matcher-local 重复元数据被删除后，才可以把目标类型称为已完成；单纯重命名不算
迁移完成。

评审发现“插件负责……”这类笼统表述时，必须改为上表中的具体责任；若没有
对应权威，先补最小目标契约和边界测试，再写业务实现。

## 过渡边界准入

开始实现前，先对照 `ARCHITECTURE.md` 的“Transition Inventory And Admission
Rule”。每个改动只允许属于以下三种之一：

1. 扩展已有 `target` 契约；
2. 修复 `baseline` 可见行为，且不增加新的依赖方向；
3. 让一个 `transition` 责任减少一个消费者、一个持久化读写路径或一个平台泄漏。

以下情况必须暂停实现并先补最小设计，而不是把需求继续接到现有模块：

- service 构造函数需要 `OneBotReferenceResolver`、`MessageTarget`、
  `OneBotDelivery`、NoneBot `Bot` 或 CQ 消息；
- service 的公开方法以 `group_id`、`qq_user_id`、`target_type` 之类的传输
  身份为业务参数，而不是接收 `ActorRef`、`ConversationRef` 或领域实体 ID；
- 为了一个新命令、推送或缓存增加第二份关键词、路由、退订、别名或状态表；
- 新代码需要从 renderer、plugin 或运行时 bridge 反向读取数据库、配置或业务
  服务；
- 计划以“先兼容两套路径”为理由，在正常运行时加入双读、双写或默认回退。

遇到这些信号时，设计记录必须写明：目标 port 或值对象、现有行为如何由平台
适配器保留、旧路径减少的范围、删除条件和针对性的防扩张测试。只有一次性停机
迁移工具可以读取旧 schema；它不属于服务正常运行路径。

## 文档同步纪律

架构文档不是事后说明。每个改变目标契约、过渡桥接或完成条件的提交，必须同时
更新 `ARCHITECTURE.md` 和本约定中对应的描述。更新至少说明：

1. 当前正常运行路径与新目标路径分别是什么；
2. 临时桥接为何仍存在，以及它不会再接收哪些新职责；
3. 删除桥接的明确前置条件和验证证据；
4. 已完成的迁移样例可被后续工作复用的边界。

代码和文档发生矛盾时，不得通过模糊措辞保留两种解释。先以已验证代码为事实，
再把目标和未完成项标记为 `transition`，直到单一路径真正完成。代码审查发现
过时的“唯一契约”“当前实现”或迁移状态描述时，应在同一工作项修正它。

### 架构变更登记

凡是改变一个职责的权威归属、平台边界、数据 schema 或直接命令契约，设计记录
和提交说明还必须给出以下最小登记：

| 项目 | 要求 |
| --- | --- |
| 旧权威 | 当前由哪个类型、模块或 schema 承担；若没有旧路径，明确写“新增”。 |
| 新权威 | 目标唯一正常路径及其所在层次。 |
| 过渡边界 | 旧路径还保留什么、明确不再接收什么新职责。 |
| 删除条件 | 哪些调用方、数据或验证完成后才能删除旧路径。 |
| 合并说明 | 若跨分支修改过同一职责，说明按何种 target/transition/baseline 判断收口。 |

这份登记可以简短，但不得用“重构”“优化”代替具体所有权描述。它既是评审依据，
也是下一次合并时的语义上下文。

## 跨仓库数据契约

涉及 `seerapi`、`seerapi-models`、`IronsBot` 或私有扩展的数据能力，先确定
哪一个仓库拥有“事实生成”，哪一个仓库拥有“运行时消费”。禁止因为下游暂时
缺字段，就在插件、服务或渲染器中重新猜测官方数据。

1. `seerapi` 负责提取、规范化、关联、资源转换、歧义记录和发布 schema。
2. `seerapi-models` 负责稳定的数据模型；新增字段必须明确它属于原始数据、
   已解析事实，还是诊断记录。
3. `IronsBot` 的 `integrations.seer_data` 负责读取已发布事实并转换为服务/渲染
   所需视图模型；renderer 不读 SQL、不下载 SWF、不根据文本猜关联。
4. 一个数据能力的提交顺序是“构建和模型 -> 真实 release 验证 -> 消费者”。
   消费者不得依赖未发布 schema，也不得用旧表双读掩盖版本不匹配。
5. 数据契约必须至少有：构建期单测、消费者 repository 单测、一个真实 release
   或生产等价 SQLite 的 smoke test，以及 schema/必需表校验。

若 release 未包含新事实，用户可见行为必须明确为“数据暂不可用”或保留已经
验证的旧功能；绝不静默回到运行时模糊匹配。发布失败要保留 `/更新数据` 的恢复
能力和管理员诊断日志。

## 提交与迁移纪律

一次提交只能完成一个可验证的职责边界。提交前：

- 读取并保留用户已有的未提交改动；不使用 `git add .`，不提交 `outputs/` 或
  生成物。
- 不为迁移留下长期旧接口包装、双读、双写或隐式回退。迁移工具必须支持
  dry-run、校验、原子替换、备份和重复执行。
- 数据/配置不兼容时，明确失败并给出恢复路径；不能静默猜测、丢数据或降级成
  错误结果。
- 在提交说明中标注目标契约、迁移状态、验证命令和回滚点。

提交后应能独立运行针对性测试；阶段结束才运行完整回归、静态分析、编译与
部署 smoke test。除非用户明确要求，不推送、不改生产数据、不读取或写入
秘密配置。

## 进度与预计时间

所有持续任务使用两层以上进度：总任务、当前阶段和当前小任务。报告格式：

```text
总体   [████░░░░░░] 40%  预计剩余 6 小时
阶段   [███░░░░░░░] 30%  预计剩余 90 分钟
当前项 [██████░░░░] 60%  预计剩余 25 分钟
```

进度以“已经验证完成的工作项”估算。调查发现范围变化时，立即说明新的估计
与原因；遇到阻塞时说明阻塞点、已验证事实和下一步，不用笼统的百分比掩盖。
每完成一个小任务，更新状态而不是把所有任务留到最后一起标记完成。

## 阶段完成定义

一个阶段只有同时满足以下条件才能标记完成：

1. 目标契约已经成为该职责的唯一正常运行路径。
2. 旧桥接路径、旧配置字段和旧持久化读写已删除，或有明确的后续阶段、删除
   条件和临时防扩张测试。
3. 数据迁移有可复跑工具、备份、校验和回滚说明。
4. 架构边界测试、相关单测、静态检查、编译检查与所需 smoke test 已实际通过。
5. 文档反映真实代码状态，且没有把当前过渡实现误写成长期唯一契约。

如果某项没有完成，阶段保持进行中，并记录剩余项。宁可留下诚实的进度，也
不要用“基本完成”掩盖双路径或未验证风险。
