# IronsBot 架构工作约定

本文规定架构改动如何被设计、实施、审查与收口。它补充
[ARCHITECTURE.md](../ARCHITECTURE.md)：后者定义代码目标与边界，本文定义
后续工作如何持续向该目标推进。

## 设计来源与冲突处理

`ARCHITECTURE.md` 是长期架构目标的唯一规范来源；当前代码、旧设计记录和
过渡实现都不是新设计的授权。每次开始跨模块工作前，先标明它处理的是
`target`、`transition` 还是 `baseline` 契约。

当新版阶段计划与文档中的旧表述不一致时：

1. 以经确认的新版阶段计划为目标；
2. 在同一工作项中修正文档，使“当前实现”“迁移桥接”和“最终目标”明确分开；
3. 不用兼容层、第二份清单或双读逻辑回避冲突；
4. 在代码尚未迁移前，如实保留 `transition` 状态和删除条件。

例如，标准 NoneBot TOML 插件清单与配置化的清单 profile 选择器属于目标
插件装载方式；禁止的是额外的反射发现、应用私有模块列表或运行时服务定位器。
当前标准 TOML 先声明需要在本地插件前加载的第三方依赖，再直接发现每个内置
本地插件。临时 OneBot bootstrap 仅适配已配置的私有扩展，不能因它仍在运行而
被误当成未来插件、命令或生命周期的权威。

## 先设计，再落代码

每个任务开始前必须写出最小设计记录。它可以是一段简短说明，也可以是
完整计划，但必须包含：

| 项目 | 必须说明的内容 |
| --- | --- |
| 目标 | 用户或系统真正要解决的问题，而不是准备修改的文件名。 |
| 契约状态 | `target`、`transition` 或 `baseline`；含义以 `ARCHITECTURE.md` 为准。 |
| 所有权 | 领域服务、端口、仓储、渲染器或插件中谁负责此行为。 |
| 复用 | 已有接口如何复用；若新建接口，为什么它是通用的最小边界。 |
| 范围 | 涉及的仓库、公开行为、配置、数据结构及不在本次范围内的事项。 |
| 数据 | 数据来源、主键、生命周期、迁移和回滚方式。 |
| 验证 | 有针对性的测试、静态检查、编译检查和必要的真实流程检查。 |

不能因为某个插件、SQLite 文件、正则或后台任务已经存在，就把新需求继续
堆到那里。相同语义的输入、身份、命令、状态、通知或渲染需求，应先寻找
现有通用接口；没有合适接口时，创建有明确领域归属的小接口。不得用
`utils`、`shared`、`common`、全局服务定位器或万能仓储掩盖所有权。

## 代码层次检查

在实现前和代码审查时，逐项确认：

1. 插件仅做事件适配、调用服务和发送结果；不在插件中拥有可复用业务规则。
2. service 不导入 NoneBot、OneBot、QQ Official 或具体插件类型。
3. renderer 只接收视图模型与资源，不读 SQL、不发 HTTP、不猜业务关联。
4. integration 实现明确端口；它不决定用户文案、权限或产品策略。
5. 配置、帐号、群号、链接、令牌和部署选择不写死在业务代码。
6. 同类命令只在 `CommandCatalog`/`CommandContract` 处登记一次；帮助、戳一戳
   和 AI 认领都从同一描述查询。
7. 所有需要赛尔玩家 ID 的位置复用 `PlayerIdResolver`；实体别名复用统一别名
   解析契约，实体自己的规范化与存储仍归实体所有。
8. 平台身份使用不透明字符串 `ActorRef`/`ConversationRef`；OneBot QQ 号与
   QQ Official OpenID 不隐式互转。
9. 正常运行路径只读写一种 schema；旧数据仅由停机的一次性迁移工具处理。
10. 新生产 Python 模块必须遵守 800 行限制，并按真实职责拆分，不能把代码
    移进无归属的辅助文件来规避检查。
11. 平台身份在持久化层只使用 `ActorRef` / `ConversationRef` 的独立列；QQ
    数字只能存在于 OneBot 适配边界。旧 SQLite 的列形状只能由停机迁移工具
    读取，运行时代码不得双读、补列或懒迁移。
12. 迁移到标准 NoneBot 清单的插件必须同时拥有自己的 `PluginMetadata`、
    `PluginContribution` 和直接命令描述；不得把 matcher 留在中央桥接、
    把帮助或命令元数据留在另一处。
13. 迁移出站消息时保留原有发送语义：`OutboundMessenger.send()` 是主动推送，
    必须经过目标平台的队列、限流和退订策略；`reply()` 才是对当前事件的即时
    回复。不能因为换成通用端口而绕过防刷屏、路由或失败回滚。
14. 通知服务的收件人必须使用 `ActorRef` 或 `ConversationRef`；OneBot 数字
    目标、`MessageTarget`、`OneBotDelivery` 和 CQ 消息只能留在 OneBot 适配层。
    迁移中的适配器可以复用旧投递链以保留队列、退订和限流，但不得把这些类型
    重新传回 service。

## 插件术语与权威边界

不能再把插件相关对象统称为“唯一插件契约”。它们职责不同，后续设计和代码
审查必须使用准确名称：

| 需要描述的事情 | 唯一权威 |
| --- | --- |
| 插件静态身份与 NoneBot 元数据 | `PluginMetadata` |
| 插件安装时提交 matcher、job、hook 等运行时贡献 | `PluginContribution` |
| 用户可输入命令的语法、示例、权限、帮助、戳一戳与 AI 认领 | `CommandCatalog` / `CommandContract` |
| 某个用户或会话是否有功能权限 | feature-policy service |
| 进程生命周期、后台任务与关闭顺序 | `ApplicationLifecycle` |

`PluginDefinition` 已退出当前架构。除迁移记录或 Git 历史说明外，不得在新代码、
测试、计划、图示或文档中重新引入它，也不得以“临时方便”为由恢复中央插件注册
表。`PluginContribution` 只是一项插件局部的运行时提交记录，不能承担命令目录、
权限策略、帮助布局或跨插件生命周期等第二份权威。

评审发现“插件负责……”这类笼统表述时，必须改为上表中的具体责任；若没有
对应权威，先补最小目标契约和边界测试，再写业务实现。

## 过渡边界准入

开始实现前，先对照 `ARCHITECTURE.md` 的“Transition Inventory And Admission
Rule”。每个改动只允许属于以下三种之一：

1. 扩展已有 `target` 契约；
2. 修复 `baseline` 可见行为，且不增加新的依赖方向；
3. 让一个 `transition` 责任减少一个消费者、一个持久化读写路径或一个平台泄漏。

以下情况必须暂停实现并先补最小设计，而不是把需求继续接到现有模块：

- service 构造函数需要 `OneBotReferenceResolver`、`MessageTarget`、
  `OneBotDelivery`、NoneBot `Bot` 或 CQ 消息；
- service 的公开方法以 `group_id`、`qq_user_id`、`target_type` 之类的传输
  身份为业务参数，而不是接收 `ActorRef`、`ConversationRef` 或领域实体 ID；
- 为了一个新命令、推送或缓存增加第二份关键词、路由、退订、别名或状态表；
- 新代码需要从 renderer、plugin 或运行时 bridge 反向读取数据库、配置或业务
  服务；
- 计划以“先兼容两套路径”为理由，在正常运行时加入双读、双写或默认回退。

遇到这些信号时，设计记录必须写明：目标 port 或值对象、现有行为如何由平台
适配器保留、旧路径减少的范围、删除条件和针对性的防扩张测试。只有一次性停机
迁移工具可以读取旧 schema；它不属于服务正常运行路径。

## 文档同步纪律

架构文档不是事后说明。每个改变目标契约、过渡桥接或完成条件的提交，必须同时
更新 `ARCHITECTURE.md` 和本约定中对应的描述。更新至少说明：

1. 当前正常运行路径与新目标路径分别是什么；
2. 临时桥接为何仍存在，以及它不会再接收哪些新职责；
3. 删除桥接的明确前置条件和验证证据；
4. 已完成的迁移样例可被后续工作复用的边界。

代码和文档发生矛盾时，不得通过模糊措辞保留两种解释。先以已验证代码为事实，
再把目标和未完成项标记为 `transition`，直到单一路径真正完成。代码审查发现
过时的“唯一契约”“当前实现”或迁移状态描述时，应在同一工作项修正它。

## 提交与迁移纪律

一次提交只能完成一个可验证的职责边界。提交前：

- 读取并保留用户已有的未提交改动；不使用 `git add .`，不提交 `outputs/` 或
  生成物。
- 不为迁移留下长期旧接口包装、双读、双写或隐式回退。迁移工具必须支持
  dry-run、校验、原子替换、备份和重复执行。
- 数据/配置不兼容时，明确失败并给出恢复路径；不能静默猜测、丢数据或降级成
  错误结果。
- 在提交说明中标注目标契约、迁移状态、验证命令和回滚点。

提交后应能独立运行针对性测试；阶段结束才运行完整回归、静态分析、编译与
部署 smoke test。除非用户明确要求，不推送、不改生产数据、不读取或写入
秘密配置。

## 进度与预计时间

所有持续任务使用两层以上进度：总任务、当前阶段和当前小任务。报告格式：

```text
总体   [████░░░░░░] 40%  预计剩余 6 小时
阶段   [███░░░░░░░] 30%  预计剩余 90 分钟
当前项 [██████░░░░] 60%  预计剩余 25 分钟
```

进度以“已经验证完成的工作项”估算。调查发现范围变化时，立即说明新的估计
与原因；遇到阻塞时说明阻塞点、已验证事实和下一步，不用笼统的百分比掩盖。
每完成一个小任务，更新状态而不是把所有任务留到最后一起标记完成。

## 阶段完成定义

一个阶段只有同时满足以下条件才能标记完成：

1. 目标契约已经成为该职责的唯一正常运行路径。
2. 旧桥接路径、旧配置字段和旧持久化读写已删除，或有明确的后续阶段、删除
   条件和临时防扩张测试。
3. 数据迁移有可复跑工具、备份、校验和回滚说明。
4. 架构边界测试、相关单测、静态检查、编译检查与所需 smoke test 已实际通过。
5. 文档反映真实代码状态，且没有把当前过渡实现误写成长期唯一契约。

如果某项没有完成，阶段保持进行中，并记录剩余项。宁可留下诚实的进度，也
不要用“基本完成”掩盖双路径或未验证风险。
