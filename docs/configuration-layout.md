# 配置布局与新增功能指南

`config.example.toml` 是部署者阅读和维护机器人的主要入口。它的章节顺序按用户可见功能与运行依赖组织，
而不是按 Python 包、服务类或最后一次修改的文件组织。

新增项目时，先确定它依赖什么，再确定配置应放在哪里；不要因为实现代码位于某个模块，就把 TOML 表随意放在
文件末尾。

## 章节地图

| 章节 | 放入什么 | 典型配置 |
| --- | --- | --- |
| 基础与授权 | 机器人进程、路径、日志、别名、功能包与访问策略 | `[bot]`、`[paths]`、`[features.*]`、`[runtime.*]` |
| 对话、消息与推送 | AI、命令行为、QQ 消息、活动、B 站与本地图片回复 | `[ai]`、`[messaging.*]`、`[activity]`、`[bilibili.*]`、`[pet_config]` |
| 赛尔实时无头查询 | 需要登录赛尔服务器或发送游戏封包的任何功能 | 账号库、`[operations.headless]`、`[seer.player.*]`、`[seer.rank.*]`、`[seer.team.*]`、`[seer.lucky_skin_window]`、私有阵容扩展 |
| 赛尔本地资料与展示 | 只读取已同步 SQLite、资源文件或渲染缓存的赛尔功能 | `[seer.mintmark]`、`[seer.new_content]`、`[seer.season]`、`[seer.render]`、`[seer.external_references]` |
| 数据同步与生命周期 | 下载或构建数据、启动通知、镜像维护和重启 | `[operations.data_sync]`、`[operations.startup_notice]`、`[operations.docker_update]`、`[operations.restart]` |

## 放置决策

按下面顺序判断一个新配置项应放在哪里：

1. 它是否会通过 `HeadlessGame`、公共无头池或专用短时会话登录赛尔服务器并发送封包？是则放入“赛尔实时无头查询”。
2. 它是否只读取已同步的 SQLite、静态资源，或控制图片/文本展示？是则放入“赛尔本地资料与展示”。
3. 它是否主要控制 QQ 指令、AI、通知、订阅、外部平台推送或本地回复素材？是则放入“对话、消息与推送”。
4. 它是否控制数据构建/下载、进程启动、镜像、重启或 Docker？是则放入“数据同步与生命周期”。
5. 它是否定义身份、路径或所有功能共享的权限？是则放入文件开头的“基础与授权”。

若一个功能跨越多章，将每个字段放到它实际控制的边界，而不是建立一个混杂的大表。例如：

- 公共无头账号的连接与池配置在 `[operations.headless]`，紧跟账号库；玩家、战队、翻榜和私有阵容都复用它。
- 排名范围、翻页与后台刷榜属于 `[seer.rank.*]`，因为它们控制榜单查询本身；无头池不为某个榜单单独再建账号配置。
- 新增内容菜单只读同步 SQLite，因此位于 `[seer.new_content]`，而不与翻榜配置混放。
- 幸运橱窗需要专用游戏会话，所以位于实时无头查询章；其缓存路径仍是持久业务数据，不应挪入可删除的 `cache/`。

## 排列规则

- 父表后紧跟它的子表。例如 `[seer.rank]` 后紧跟 `[seer.rank.page_refresh]` 与其子表；不要把子表移动到文件另一端。
- `[[array.of.tables]]` 保持连续，且保留声明顺序。远程构建步骤、定时任务与账号列表的顺序都可能具有业务含义。
- 公共资源按使用者的主流程放置。`[operations.headless]` 的名字虽然在 `operations` 下，但它是实时查询池的基础，应与账号库和查询配置相邻。
- 私有扩展的包加载器与其当前主流程相邻；扩展自己的 `settings.<name>` 则按功能归类。当前私有阵容依赖公共无头池，所以两者都在实时查询章；未来纯消息或静态资料扩展不应因此照抄到该处。
- 密钥、密码、Token 和可变部署路径仍使用环境变量或既有路径配置；不要为了“集中”把密钥写入 TOML。
- 需要用户配置的行为必须有中英文注释，写明默认值、影响范围、可接受的别名/ID 格式，以及与相邻配置的关系。

## 新功能接入清单

新增可配置项目时，按以下步骤完成，而不是只增加一个 Pydantic 字段：

1. 先按本指南选定章节和父表，决定字段是否是运行时、消息推送、无头查询、静态资料或运维配置。
2. 在配置模型中定义严格类型、默认值与字段错误；引用 QQ、群或赛尔账号时复用统一解析器。
3. 在 `config.example.toml` 的对应父表附近加入中英文注释、默认值和最小示例；不要删改无关注释或改变既有数组顺序。
4. 若功能需要帮助、权限或命令目录，同时登记 feature、策略、命令描述和回归测试。
   适合被戳一戳随机提示的直发命令还要设置 `show_in_poke=True`；命令 ID 必须
   稳定。镜像构建会按 Git 首次引入该 ID 的时间，临时提高它的戳一戳随机权重。
5. 增加配置加载测试，验证默认值、错误输入和至少一个实际功能路径；然后运行 TOML 解析、相关测试与 `git diff --check`。
6. 新增循环定时任务时，墙上时刻统一使用 `HH:MM:SS` 并通过 `ScheduledClockTime` 与 `JobRegistry` 注册；不要手动拆分字符串或写死 `second=0`。持续时间（超时、冷却、重试等待）继续使用 `*_seconds`，不要伪装成钟表时间。

## 评审问题

提交前回答这些问题：

- 部署者能否只看相邻配置就知道这个字段依赖无头登录、SQLite，还是外部平台？
- 该字段是否和同一用户流程的配置相邻？
- 是否错误地复制了账号、缓存、额度或权限配置，而本应复用既有公共服务？
- 是否保留了示例中的字段、注释和有序数组？
- 配置路径、别名和环境变量是否遵循已有的统一解析与密钥边界？

满足这些条件，配置文件会随着项目增长仍然保持可读，而不是变成按实现历史堆叠的清单。
